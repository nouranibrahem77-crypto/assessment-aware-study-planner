# OULAD data dictionary

This dictionary covers the five source CSVs required by the ingestion workflow.
The definitions follow the OULAD documentation and published dataset paper.
Values are joined by the identifiers shown below; no demographic columns are
read or used by this task.

## Shared conventions

- `code_module` identifies a course module (for example, `AAA`).
- `code_presentation` identifies a particular course run. Codes such as
  `2013B`, `2013J`, `2014B`, and `2014J` sort chronologically by year, then by
  B (February start) and J (October start).
- Date fields in these tables are integer day offsets from the start of the
  presentation, not calendar dates. A missing assessment deadline is left
  missing by the source.
- `id_student` is the dataset's student identifier; `id_assessment` and
  `id_site` link assessment and VLE tables respectively.

## `courses.csv`

One record describes a course presentation.

| Column | Meaning |
| --- | --- |
| `code_module` | Course module identifier. |
| `code_presentation` | Course presentation identifier. |
| `module_presentation_length` | Presentation duration in days. |

## `assessments.csv`

One record describes an assessment scheduled for a course presentation.

| Column | Meaning |
| --- | --- |
| `code_module` | Course module identifier. |
| `code_presentation` | Course presentation identifier. |
| `id_assessment` | Unique assessment identifier used by `studentAssessment.csv`. |
| `assessment_type` | Assessment category, such as TMA, CMA, or Exam. |
| `date` | Deadline as a day offset from presentation start; may be missing. |
| `weight` | Assessment contribution to the course grade, expressed as a percentage. |

## `studentAssessment.csv`

One record describes a student's recorded assessment submission/result.

| Column | Meaning |
| --- | --- |
| `id_assessment` | Assessment identifier linking to `assessments.csv`. |
| `id_student` | Student identifier. |
| `date_submitted` | Submission day offset from presentation start. |
| `is_banked` | Indicator for a result carried forward from a prior presentation. |
| `score` | Recorded assessment score on the source's 0–100 scale; may be missing. |

## `studentVle.csv`

One record gives a student's daily interaction count for a VLE resource.

| Column | Meaning |
| --- | --- |
| `code_module` | Course module identifier. |
| `code_presentation` | Course presentation identifier. |
| `id_student` | Student identifier. |
| `id_site` | VLE resource identifier linking to `vle.csv`. |
| `date` | Interaction day offset from presentation start. |
| `sum_click` | Number of recorded clicks by the student on that resource on that day. |

## `vle.csv`

One record describes a VLE resource available for a course presentation.

| Column | Meaning |
| --- | --- |
| `id_site` | VLE resource identifier used by `studentVle.csv`. |
| `code_module` | Course module identifier. |
| `code_presentation` | Course presentation identifier. |
| `activity_type` | Type/category of VLE activity. |
| `week_from` | Planned first week of use; may be missing. |
| `week_to` | Planned last week of use; may be missing. |

## Generated FFF feature files

`data/processed/fff_train.csv`, `fff_validation.csv`, and `fff_test.csv` contain
one retained student-assessment row per non-banked, valid score submitted on or
before its assessment deadline. They are generated by
`python scripts/make_features.py`; `fff_preprocessing.json` records the fixed
split, source file hashes, feature schema, and cutoff assumptions. These outputs
are ignored by Git.

| Column or prefix | Meaning |
| --- | --- |
| `code_module`, `code_presentation`, `id_student`, `id_assessment` | Stable audit and join identifiers; not model inputs. |
| `assessment_type_*` | One-hot assessment type indicators. Categories come from training presentations only. |
| `assessment_weight` | Published assessment weight; `assessment_weight_available` distinguishes a missing weight from zero. |
| `assessment_deadline_day` | Published deadline day offset from presentation start. |
| `weeks_since_course_start` | Deadline day divided by seven. |
| `previous_assessment_score_lag_N` | Score for the Nth preceding scheduled assessment with a strictly earlier deadline. Blank if that student's score is unavailable; the paired `_available` column is 0/1. |
| `click_<group>_week_N` | Sum of `sum_click` in one of four consecutive 7-day windows before the deadline. |
| `target_score` | Current assessment score (0–100); label only and never an input feature. |

The prediction cutoff is the start of deadline day D. Click windows are
`[D-28, D-21)`, `[D-21, D-14)`, `[D-14, D-7)`, and `[D-7, D)`; events on or
after D are excluded. FFF VLE activity types are grouped as:

- `content_navigation`: `dataplus`, `dualpane`, `folder`, `glossary`, `homepage`,
  `htmlactivity`, `oucontent`, `page`, `repeatactivity`, `resource`, `subpage`,
  `url`.
- `assessment_activity`: `questionnaire`, `quiz`.
- `collaboration`: `forumng`, `oucollaborate`, `ouelluminate`, `ouwiki`.

A zero click count means no matching event in a known complete window;
unavailable prior scores or click counts affected by invalid/unmatched events
remain blank. Prior scores are restricted to non-banked, valid on-time results
with submission before D. OULAD has no score-release timestamp, so using a prior
result after its earlier deadline is a documented proxy, not a verified fact.
No demographic fields are used.

The fixed row-level partition is train = 2013B and 2013J, validation = 2014B,
and test = 2014J. Rows are never randomly reassigned.

Feature generation supports two score configurations. `strict` (the default)
excludes every previous-assessment-score feature. `proxy` includes a prior score only for the
same student and presentation, on a strictly earlier scheduled assessment with
a non-banked, valid score submitted on time. Because OULAD does not record grade
release time, proxy availability is an unverified assumption. Select a mode
with `python scripts/make_features.py --score-mode strict` or
`python scripts/make_features.py --score-mode proxy`; the selected mode is
recorded in the preprocessing manifest.
